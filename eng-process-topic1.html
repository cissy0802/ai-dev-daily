工程流程改造

agent 写大部分代码之后，评审、CI、迁移和交付流程要怎么改？

40 篇来源 · 更新于 2026-11-12 · BigCat

// 目前能学到的

  1. agent 放量后，瓶颈先落到人工评审和共享基础设施上，所以推广之前就该压测 CI、merge queue 和 Git 的并发能力。独立研究 Harvard/Jellyfish 发现采纳 agent 后「提交评审→批准」时长增加 56.1%，issue/epic 的增幅远小于代码量增幅；厂商侧 Anthropic CI、OpenAI Pando、Linear 也都被 CI 或 Git 压垮过。注意 Linear 的做法（runner、分片、门禁瘦身）不需要实验室条件，而自研 VCS 连 Anthropic 自己都不建议照搬。（多个组织）
  2. 人工审批应按变更风险分层，而不是一律要人看：风险等级由分类器按变更判定，不按作者判定；低风险全绿就自动合并，auth/计费/安全区保留 code owner，bot 批准不能替代人，新提交使批准失效（Claude Code 评审、Anthropic 安全 SDLC）。这份信任要按代码区域花半年以上逐步放开（Cat & Thariq 访谈），GitHub 也提醒涉及授权、计费、隐私的改动，diff 再干净也不算便宜（The cost of saying yes）。（多个组织）
  3. 先建验证手段，再放手让 agent 生成。迁移、重写、维护这类有参照物的工作最适合做第一批试点：可以用旧实现当 oracle 做差分测试加影子流量（PostHog），用与实现语言无关的测试套件验收（Bun），每个增量 PR 都过全量 E2E（GitHub Rust 迁移），或者先从规格生成测试、在真实系统上校准（AWS Emulator）。删死代码、清过期 flag 时，要求 agent 附上不可达的证据（OpenAI 维护）。没有自动化的「完成」信号，就只是在看着一个生成器干活（Meta Forum）。（多个组织）
  4. AI reviewer 要设计成多个窄职责、能自证、可度量噪声的系统，不要靠一个大 prompt。具体做法：多 agent 并行找 bug，再由另一组投票确认，每条发现都要附「证明」，用历史事故和回滚 PR 建 eval，限制评审轮数（Claude Code 评审）；评审规则要小、有作用域，宽泛规则会制造噪声（OpenAI 评审规则）；多家模型交叉审，再由主 agent 去掉误报（Nolan Lawson）。证据上要留个心：常被引用的 16%→54% 衡量的是「收到实质评论的 PR 占比」，不是缺陷检出率；Meta 的 60% 真阳性率是工程师自报的（Meta JiTTesting）。（多个组织）
  5. 把评审人和老员工脑子里的规则写成 agent 能读、CI 能跑的东西：同一错误出现两次就写成规则（Meta Forum），发现新的漏洞类别就回写到 CLAUDE.md 或 skill（Anthropic 安全 SDLC），把 CI 约束写进生成测试的 skill（Linear），agent 想绕过检查之后就加上「未经同意不得改 E2E 测试」这样的规则（GitHub Rust 迁移）。出了问题，修的是生成代码的流程，不去手改产物（Bun）。（多个组织）
  6. 代码可以交给 agent 写，但谁为这次改动负责必须由人显式承担，各家只是在 PR 描述的处理上有分歧。Kenton Varda 团队禁止 AI 写描述，把它当作「作者真懂这次改动」的证明；Simon Willison 则让人写首段，agent 的长描述折叠起来。Ladybird 更进一步，因为 PR 体量已经不再代表投入和可信度，干脆关闭了公开 PR。对 inner-source 仓库来说，可以先从 PR 模板（意图、风险、回滚方式）和受信作者名单做起。（多个组织）
  7. 个人提速不会自动变成团队提速，度量口径也不能混用。Microsoft Digital 的教训是传统 SDLC 每次交接都会丢意图，必须改流程（spec 驱动）才能拿到团队收益；Nolan Lawson 把 AI 用在质量上，结果速度不升反降。Anthropic 同一家就有「>80% 合并代码行」（When AI builds itself）和「90%+ 核心库合并变更」（Fable 5.2）两种口径，作者自己也说这两个数不能混用，跨组织就更不能直接比较。（多个组织）

Google 的多 agent harness 靠「按步骤切分上下文 + 独立证伪器 + 不看原作者推理的审计 agent」跑多日任务，并用它在生产基础设施上拿到可量化收益

Google2026-11-13 · Advancing science & engineering with Antigravity’s /teamwork

这是一篇产品/科研成果帖，其中有 Google 内部工程用法。/teamwork 的设计：每个专职 agent 只拿到当前步骤需要的文件和工具；协调者把任务交给全新上下文的继任者；critic/auditor 在干净上下文里复核，看不到原作者的推理；候选解交给 Lean、原封不动的测试套件、模拟器、硬件计数器等「证伪器」自动判定。大规模迁移的做法是：按依赖顺序调度模块，每个叶子模块都链接原始、未改动的测试，防止 agent 打桩或改测试。内部落地包括：两周把 Zircon 内核剩余 C++ 改写成约 80 万行 Rust；Borg 调度优化上线 2 个改动；全机队内存优化；TPU kernel 优化中先让 agent 造 23 秒的代理评测，再定期用完整硬件跑校准排序。

  • To prevent this, /teamwork partitions context by construction: each specialized agent receives only the exact files and tools it needs for a specific step.
  • Building on the initial 25% port of the Zircon microkernel, a two-week Argon campaign rewrote the remaining C++ code, adding about 800,000 lines of safe Rust that pass all kernel unit tests and boot on arm64 hardware.
  • Fleet-wide memory optimization: Building on the initial Argon memory efforts, we analyzed fleet-wide metrics, as well as internal memory saving past successes, and created reusable /teamwork workflows that have identified memory saving opportunities, surpassing our initial savings estimates of 1 PiB.
  • Borg agentic scheduling: Built on /teamwork and /boost, Borg’s agentic workflow for scheduling optimization shipped 2 successful changes, resulting in a 24% reduction in TPU workload preemption on some hardware types, while preserving workload SLOs and cluster utilization.
口径：Zircon：「通过全部内核单元测试并能在 arm64 启动」是验收标准，没说是否已合入生产、有无人工评审或后续缺陷。内存：是「已识别的」节省机会超过 1 PiB，不是已释放量（对比 Argon 帖里已释放 300 TiB）。Borg：24% 只在「部分硬件类型」上，总共 2 个改动，没给基线和时间窗。没有任何 token/算力成本数据。
能借鉴的：想让 agent 跑多日任务，先把三件事做成结构而不是提示：① 每一步只给需要的文件和工具，长任务定期换新上下文接力；② 每类产出都配一个机器可判的证伪器（编译器、原始测试、模拟器），没有证伪器的任务先别交给长时 agent；③ 复核 agent 不读原作者的推理，只看产物。做代码迁移时，按依赖拓扑排期、只用原始测试验收。完整评测太慢时，可以先让 agent 造快速代理指标，再用完整评测定期校准排序（Kendall 相关）。前提：已有可信、可自动跑的测试或评测。
冷水：厂商自报、挑选案例，主体是科研成果和产品推广；生产收益只列了少数几项，没有失败率、成本和人力投入；Google 规模的基础设施（Borg、TPU、机队级 profiling）多数组织没有。

AWS 让 agent 先从 API 规格生成并在真实 AWS 上校准测试，再实现模拟器直到通过

AWS2026-11-11 · AWS Emulator and the engineer's job when agents write the code

AWS 发布全部由 agent 编写和测试的本地 AWS 模拟器：以 Smithy 公开 API 模型为规格，agent 先从规格派生端到端「fidelity test」并在真实 AWS 上修正到通过（使测试记录真实行为），再构建模拟器直到通过同一测试；agent 团队持续对照真实 AWS 找差距；每个变更都经 merge gate（多个安全 agent 对抗评审 + 通用代码评审 + 禁止 agent 触碰特定代码的确定性检查）。作者自述用 Kiro 重建当年 Alf 复制引擎：没有验证手段时盯了四个晚上无果，有了 spec 和测试环境后约两小时完成。

  • Matt began with SQS alone, and when he gave Kiro one prompt describing this approach, it returned a passable first version of an SQS emulator in about 15 minutes.
  • All of AWS Emulator’s code was written and tested by agents, and it is built from more than 400 API models covering more than 200 AWS services.
  • Once it had a spec and a test environment, the rebuild took about two hours.
口径：Simon 的链接帖补充：项目前三周有 29,684 次提交（来自 GitHub 仓库）。「四个月 vs 两小时」是作者个人对比，前者为当年人工首次构建。
能借鉴的：「先让 agent 从规格生成测试并在真实系统上校准，再让 agent 实现直到通过」是可推广的模式，适用于任何有 API 规格和真实参照系统的内部服务仿真/替代；同时说明工程师的新职责是设计 spec、测试与 merge gate，而不是写代码。
冷水：厂商发布配套博文，带 Kiro 产品宣传；稳健性、真实使用效果未给数据；仓库有「things-that-do-not-work」目录记录未对齐行为。

哈佛基于 655 家公司的研究发现，AI agent 让代码量大增，但 issue 完成增幅小得多，瓶颈卡在代码评审

Harvard2026-11-09 · Artificial Intelligence in the Firm: Bottlenecks in Software Production

哈佛两位经济学者用工程分析平台 Jellyfish 的专有数据（GitHub、Jira、日历共 4.45 亿条工作事件，655 家公司、72 万员工），按企业采纳 AI 编码助手/agent 的时间差做双重差分。结论：AI 大幅增加代码产出，但 Jira issue/epic 等最终软件产出增幅小得多，对就业无可检测影响；瓶颈转到 code review——等审时间、审阅时长、要求修改次数都上升；79.1% 的企业已用 AI review 工具，但评审仍以人为主。

  • AI assistants lead to moderate increases in code output — 12 months after adoption, firms exhibit an increase of 30.4% in lines of code, 16.8% in commits, and 20.9% in pull requests. AI agents lead to larger additional increases in all three measures — 44.0% for lines of code, 36.0% for commits, and 35.7% for pull requests opened.
  • The effects from AI assistants are near zero, at −1.5% on issues and 3.4% on epics. The effects from AI agents are slightly larger — 13.7% on issues and 18.0% on epics — with the effect of agents on issues resolved being borderline significant.
  • We find evidence of a bottleneck in this stage: after adoption of AI agents, the average time from the code’s review submission to its approval increases by 56.1%. This change represents both an increase in the time that code waits in a “backlog,” by 59.9%, and an increase in the time after code has begun active review, by 58.5%.
  • This bottleneck is not eliminated by adoption of AI tools in the review process — 79.1% of firms have adopted AI code review tools, but still largely keep humans in the loop, with the overwhelming majority of reviews and comments being written by humans.
口径：样本为使用 Jellyfish 的 655 家软件企业（自选择：愿意买工程度量平台的公司），数据截至 2026-03；采纳时点部分由 GitHub 活动推断。论文 11-09 版数字与 Ars 10-09 报道（基于旧版：LOC +30%、review 时长 +49%）不同，以论文当前版为准。
能借鉴的：这是本批中最重要的「反面/校准」证据：只看 LOC、commit、PR 会高估 AI 效果，要同时看 issue/epic 完成、PR 等审时长、要求修改比例、评审人力占比。组织若推 agent 而不同步改造评审（风险分级、自动化验证、AI 预审），产出会卡在 review。
冷水：观察性研究，非随机；数据截止 2026-03，早于多个更强模型；作者为求职论文（Job Market Paper），有长期预测模型部分假设较强。HN 讨论与 Ars 读者评论多为对「被迫用 AI、评审被淹没」的共鸣。

OpenAI 发现 Codex 并行化后最先扛不住的是 monorepo 的 Git 后端，推广 agent 前应先压测源码管理的并发读写

  • In production, Pando cut median push latency by nearly 5x.

  • We built Pando with Codex, moving from kick-off to production, in just 10 weeks.
  • The core of Pando was designed by a single engineer, implemented by teams of agents, and deployed by a handful of engineers.
  • Multiple continuous sessions ran for hundreds of hours finding and fixing edge cases in Pando.
  • Switching to Pando improved merge reliability and reduced the latency of the median push by nearly 80%.
  • Pando has served more than 57 terabytes of Git packs in a single hour, with more than 99% of those bytes from local disk cache.
  • In our monorepo, the median packfile produced this way was under 20 KiB, and the 99th percentile was under 3 MiB.
口径：“可靠性有时低于 90%”未说明是哪类操作的成功率、统计周期。“近 5x”与“近 80%”指同一件事（中位 push 延迟），两种表述。10 周是 kick-off 到生产，未说明投入人数总量（只说核心设计 1 人、部署“少数”工程师）。未给出 agent 写的代码占比、评审方式或缺陷率。

Meta 每晚为高风险 diff 自动生成捕获测试，经多模型判官加确定性规则过滤后只推高置信结果

Meta2026-10-29 · Catching Bugs Before They Land: JiTTesting’s Human-on-the-Loop Approach at Full Scale

Meta 把用 LLM 生成“即时捕获测试”（Catching JiTTests）的研究原型部署进生产基础设施：每晚用空闲算力挑选前一天提交的高风险 diff，用两条流程生成会失败的测试（“意图感知”：推断改动意图和风险后构造变异体；“可疑 diff”：把每个改动当作 bug 生成区分行为的测试），再由多模型 LLM-as-Judge 集成和确定性规则判别器（RubFake）联合排序真/假阳性，只把高置信结果推送给工程师。采用“human-on-the-loop”：人设定标准、看聚合结果，而不是逐条审阅；工程师通常不用读测试代码，只确认行为变化是否有意。

  • As of this writing, 589 engineers at Meta (64% of our outreach) have engaged with Catching JiTTests.
  • These engineers have reported that Catching JiTTests surfaces genuinely actionable findings, with a 60% rate of true positives.
  • In the first half of 2026, Catching JiTTests played a key role in catching 74 serious (SEV) privacy bugs at the diff stage, before they landed in production and lowering the overall occurrence of privacy SEVs by 20% during that timeframe.
口径：64% 的分母是被系统触达的工程师；60% 真阳性率由参与工程师报告；“隐私 SEV 下降 20%”是同期总体变化，“played a key role”的归因方式未说明，也可能有其他因素。
能借鉴的：与 AI 代码评审互补：对高风险 diff 自动生成“证明行为变化”的可执行测试，用确定性规则 + 多模型判别过滤假阳性，只推高置信结果给作者。可用离峰算力批处理。前提：有 diff 风险评分和可运行的单元测试环境。
冷水：Meta 研究团队（Mark Harman 等）自述，配套 FSE 论文；“SEV 下降”归因较弱。

口径：关键口径说明在脚注：>80% 是「合并到生产的代码行中可归因于 Claude 的比例」，归因管线有缺口，未归因部分还包括自动生成代码，因此偏保守；而「90%+」是领导层含脚本和实验代码的估计——两个数字口径不同不可混用。8x 按「每工程师每天合并代码行」计，作者自己承认行数会高估真实生产率。4x 为 130 名研究员自报（作者认为真实值更低，并引 METR 指出自报会高估）。76% 的会话成功率由 Claude 判官判定（无需纠正即成功）。三分之一是回溯性估计。51%/64% 基于刻意挑选的 129 个「人类选择有改进空间」的时刻，不是人机公平对比。

Nolan Lawson2026-05-25 · Using AI to write better code more slowly

作者用一个 Claude skill 对每个 PR 同时调用 Claude 子 agent、Codex、Cursor Bugbot 三家找 bug 并分级，再由主 agent 自己核实排除误报、写总报告；然后让 agent 修完所有 critical/high、性价比低的 medium 跳过、critical 太多就放弃整个 PR。结果是代码库健康度和对代码的理解提高了，但速度并没有明显提升，常被拖进修复既有 bug、补测试的支线。
