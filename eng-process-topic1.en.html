Once agents write most of the code, how should review, CI, migrations, and delivery change?

42 sources · updated 2026-11-16 · BigCat

// What we can learn so far

  1. When agent volume ramps up, the bottleneck lands first on human review and shared infrastructure, so load-test CI, the merge queue, and Git concurrency before rollout. Independent research from Harvard/Jellyfish found that after agent adoption, time from review request to approval rose 56.1%, and issue/epic completion grew far less than code volume. On the vendor side, Anthropic CI, OpenAI Pando, and Linear have all been overwhelmed by CI or Git load. Note that Linear's fixes (runners, sharding, slimmer gates) need no lab conditions, while even Anthropic advises against copying its custom VCS. (multiple orgs)
  2. Human approval should be tiered by change risk, not required on everything: a classifier sets the risk level per change, not per author; low-risk changes auto-merge when green; auth/billing/security areas keep code owners; bot approval doesn't substitute for a human; new commits invalidate approval (Claude Code review, Anthropic secure SDLC). That trust is extended area by area over six months or more (Cat & Thariq interview), and GitHub cautions that changes touching authorization, billing, or privacy are never cheap, however clean the diff (The cost of saying yes). (multiple orgs)
  3. Build verification first, then let agents generate. Migrations, rewrites, and maintenance, work with a reference point, make the best first pilots: use the old implementation as an oracle for differential testing plus shadow traffic (PostHog), accept against a test suite independent of the implementation language (Bun), run full E2E on every incremental PR (GitHub Rust migration), or generate tests from the spec first and calibrate them on the real system (AWS Emulator). When deleting dead code or stale flags, require the agent to attach evidence of unreachability (OpenAI maintenance). Budget review capacity for it: Anthropic's daily maintenance routines opened 388 PRs and merged 180 after automated and human review (Claude maintenance routines). Without an automated "done" signal, you're just watching a generator work (Meta Forum); the cheapest starting point is a per-service verify skill that lets the agent run the app itself (Claude Code verification). (multiple orgs)
  4. Design AI reviewers as a system of multiple narrow roles that prove their findings and have measurable noise, not one big prompt. Concretely: several agents hunt for bugs in parallel and another set votes to confirm, every finding comes with a "proof," evals are built from past incidents and reverted PRs, and review rounds are capped (Claude Code review). Review rules should be small and scoped, since broad rules create noise (OpenAI review rules). Cross-review with multiple vendors' models, then have a main agent remove false positives (Nolan Lawson). Read the evidence carefully: the often-cited 16%→54% measures "share of PRs receiving substantive comments," not defect detection rate, and Meta's 60% true-positive rate is engineer-reported (Meta JiTTesting). (multiple orgs)
  5. Turn the rules in reviewers' and veterans' heads into something agents can read and CI can run: write a rule once the same mistake happens twice (Meta Forum), write new vulnerability classes back into CLAUDE.md or a skill (Anthropic secure SDLC), put CI constraints into the test-generation skill (Linear), and once an agent tries to get around a check, add a rule like "never modify E2E tests without approval" (GitHub Rust migration). When something breaks, fix the process that generates the code, not the output by hand (Bun). The rules themselves need protecting and pruning: read review rules only from the base branch so a PR can't change them, require at least two cases identifiable from a diff before turning a miss into a rule, and run any new gate in observe mode before enforcing (Claude Code verification). (multiple orgs)
  6. Agents can write the code, but a human must explicitly own accountability for the change; teams differ only on how they handle PR descriptions. Kenton Varda's team bans AI-written descriptions, treating them as proof that the author really understands the change; Simon Willison has a human write the first paragraph and collapses the agent's long description. Ladybird went further and closed public PRs entirely, because PR size no longer signals effort or trustworthiness. For inner-source repos, start with a PR template (intent, risk, rollback plan) and a trusted-author list. (multiple orgs)
  7. Individual speedups don't automatically become team speedups, and metrics with different bases can't be mixed. Microsoft Digital learned that the traditional SDLC loses intent at every handoff, so capturing team-level gains required changing the process (spec-driven). Nolan Lawson applied AI to quality, and his speed went down rather than up. Anthropic alone reports both ">80% of merged lines of code" (When AI builds itself) and "90%+ of merged changes in core libraries" (Fable 5.2); the authors themselves say the two can't be mixed, let alone compared directly across organizations. (multiple orgs)

The Claude Code team runs its verification layer as its own system: changes can't touch the rules that judge them, new gates go observe-then-enforce, and missed bugs become rules.

Anthropic2026-11-16 · How the Claude Code team thinks about verification
What to borrow: Steps that don't need lab conditions: 1) write a verify skill per service that spells out how to boot and click through it, and make it reliable before raising agent parallelism; 2) keep review rule files where a PR can't touch them (read from the base branch only) and bind review results to a commit SHA; 3) launch any new commit gate in observe mode, review false positives, then enforce, and allow a commit message to explain why it wasn't verified; 4) turn past incidents into a checklist with diff-readable triggers so the agent checks only matching items; 5) put a bar on turning misses into rules (at least two cases, identifiable from a diff, human-approved) and prune rules regularly. Prerequisites: agents can spin up the E2E environment on their own, and tests aren't flaky, or the agent learns to rerun instead of fix.
What they did · verbatim numbers · caveats

The Claude Code team (where Claude writes and reviews about 90% of the code) described its verification process. Each repo has a verify skill so Claude actually runs the app as a smoke test before committing (Chrome extension, mobile MCP, computer use, or a local service). Before opening a PR, Claude runs tests, build, and lint; if a check still fails after three rounds, Claude stops and pulls in a human. Code owners write their own checks. A 39-item reliability checklist gives each item a trigger readable from the diff, and Claude checks only the 3 to 10 that match. Instead of adding a second reviewer, they tune the primary reviewer's REVIEW.md, which is read only from the base branch so a PR cannot change the rules judging it; review results are tied to a specific commit. Every commit is stamped with how it was verified (including none), and a commit gate has off/observe/enforce modes, letting the next commit through after two blocks in one session. They review the reviewers using revert counts, pre-merge rejections, and a size-matched control set of clean changes. A missed bug becomes a rule only if it shows up in at least two PRs, is identifiable from a diff, survives three agents trying to disprove it, and is approved by a human in a PR. Flaky tests can't be fixed with sleeps or retries; if no root cause is found, the test is deleted with a written reason. Rule files are pruned on a routine.

  • On the Claude Code team, the vast majority of our code (~90%) is written and reviewed by Claude.
  • In internal testing around structured file generation, having a separate grader check Claude’s work against a rubric improved task success by up to 10 points over a standard prompting loop, with the largest gains on the hardest problems.
  • If a check is still failing after three rounds, Claude stops and brings in a human.
  • We maintain a reliability checklist with 39 items, each with a trigger that can be read from a diff, a check, and the incidents or PRs behind it.
  • Claude reads the diff and checks only the items whose trigger matches–usually 3 to 10–so nobody has to memorize past outages.
  • These must occur in at least two PRs and be identifiable from a diff to be considered a potential rule.
  • If at least two find the bug, it's a detectable bug.
Basis: "About 90%" has no stated basis (lines, PRs, or commits), and this time the claim is that Claude both writes and reviews it, which differs from the earlier "Claude writes about 90%" (review post). "Up to 10 points" comes from internal testing on structured file generation, not from the Claude Code repo itself, with no baseline or sample size. The 39-item checklist and 3 to 10 matches per diff describe scale only; nothing says how many issues the checklist caught. The three reviewer-quality metrics (reverts, pre-merge rejections, clean control set) are defined but no values are given.
Caveats: Vendor self-report by an Anthropic employee, and the post also promotes its own features (Code Review, /verify, hooks). It covers a single team, one that builds the agent tool itself and has built-in dogfooding and high fluency. There is almost no outcome data: nothing on how many commits the gate blocked, its false-positive rate, or what checklist matches actually found.

A Harvard study of 655 companies finds AI agents sharply increase code volume but issue completion much less, with the bottleneck in code review.

Harvard2026-11-09 · Artificial Intelligence in the Firm: Bottlenecks in Software Production
What to borrow: The most important counterweight / calibration evidence in this batch: looking only at LOC, commits, and PRs overstates AI's effect. Also track issue/epic completion, PR review wait time, share of changes requested, and share of reviewer effort. Organizations that push agents without also rebuilding review (risk tiering, automated verification, AI pre-review) will see output stall in review.
What they did · verbatim numbers · caveats

Two Harvard economists used proprietary data from the engineering analytics platform Jellyfish (445 million work events across GitHub, Jira, and calendars; 655 companies, 720,000 employees) and ran a difference-in-differences analysis on staggered company adoption of AI coding assistants/agents. Findings: AI greatly increases code output, but final software output such as Jira issues/epics rises much less, with no detectable effect on employment. The bottleneck shifts to code review: time waiting for review, review duration, and change requests all rise. 79.1% of companies already use AI review tools, but review remains mostly human.

  • AI assistants lead to moderate increases in code output — 12 months after adoption, firms exhibit an increase of 30.4% in lines of code, 16.8% in commits, and 20.9% in pull requests. AI agents lead to larger additional increases in all three measures — 44.0% for lines of code, 36.0% for commits, and 35.7% for pull requests opened.
  • The effects from AI assistants are near zero, at −1.5% on issues and 3.4% on epics. The effects from AI agents are slightly larger — 13.7% on issues and 18.0% on epics — with the effect of agents on issues resolved being borderline significant.
  • We find evidence of a bottleneck in this stage: after adoption of AI agents, the average time from the code’s review submission to its approval increases by 56.1%. This change represents both an increase in the time that code waits in a “backlog,” by 59.9%, and an increase in the time after code has begun active review, by 58.5%.
  • This bottleneck is not eliminated by adoption of AI tools in the review process — 79.1% of firms have adopted AI code review tools, but still largely keep humans in the loop, with the overwhelming majority of reviews and comments being written by humans.
Basis: The sample is 655 software companies using Jellyfish (self-selected: companies willing to buy an engineering metrics platform), with data through 2026-03; adoption timing is partly inferred from GitHub activity. The paper's 11-09 version has different numbers from the Ars report of 10-09 (based on an older version: LOC +30%, review time +49%); the current paper version takes precedence.
Caveats: Observational, not randomized; data ends 2026-03, before several stronger models. The authors' job market paper, and the long-term forecasting model rests on strong assumptions. HN discussion and Ars reader comments largely echo "forced to use AI, drowning in review."
