Claude Fable 5.2 上线：$8/$40，更快更便宜，但 API 规则收紧，自己拼 messages 的代码要先自查

Anthropic2026-11-09 · Introducing Claude Fable 5.2 and Claude Mythos 5.2

Fable 5.2（claude-fable-5-2）和 Mythos 5.2 是同一个底模，Mythos 只给通过验证计划的机构。1M context window、128k 最大输出、adaptive thinking 常开。价格从 Fable 5.1 的 $10/$50 降到 $8/$40 每百万 token，batch 减半；fast mode 最高 2.5 倍出 token 速度，$16/$80，请求里加 speed: "fast"，不用 beta header。Claude Code 2.1.321 起它就是默认的 Fable 模型。

真正要动手的是开发者文档「What's new」里列的破坏性变化：prefix check 对所有账号强制——你的代码只要改过 system、tools 或任何一条更早的 message，再把 Fable 5.2 的 thinking block 送回去，就是 400（报错信息 The block is bound to a different conversation）。临时绕过是 thinking-binding-controls-2026-08-01 header 加 prefix_mismatch_behavior: "drop_block"，代价是输出 token 可能上涨。另外：tool_choice 强制工具调用（any / 指定 tool）直接 400，要结构化输出改用 strict: true 或 JSON outputs；computer use 必须换成 computer_toolset_20260801（Bedrock 例外）；advisor tool 里 Fable 5.2 当执行者时，advisor 只能是 Fable 5.2 / Mythos 5.2。

还有一条容易踩：Fable 5.2 的 thinking block 只有 Fable/Mythos 5.2 能读。路由器把对话切回 Opus 5.5 时，这些推理会被静默丢掉（请求照样成功）。文档还提醒几处不改代码也会变的行为：prompt 里写「别想太多」在 medium 以上不管用；长任务在 low/medium effort 下可能半路收工、列个待办就停；不说清代码归属时，它倾向在现有结构上加东西、只报告邻近问题不修。

  • Over 90% of the changes merged into Anthropic’s core codebase are now written by Claude (with human guidance). — 口径：Anthropic 「core codebase」里已合并的 change；没给时间段、总量，也没定义「with human guidance」到什么程度。
  • At High effort, Fable 5.2 scores about the same as Opus 5.5’s best score (45.3% vs. 45.5%) for roughly half the cost per task — FrontierCode 2.0（衡量改动会不会被开源维护者合并），对比的是 Opus 5.5 的 Max effort。
  • the model coordinated over 1,000 subagents, working around the clock for eight days — 一名工程师从空目录让它写原型操作系统的实验，单个案例。
对你：如果你们是 Claude Code / Agent SDK / Managed Agents 构建请求，文档明说什么都不用改。自己拼 messages 的（自研 harness、中途换 tools、做历史裁剪的），切模型前先跑一遍迁移指南里的 prefix check 测试，再把 tool_choice 强制调用全局 grep 一遍。模型路由：Anthropic 自己的建议仍是 Opus 5.5 打底，Opus 高 effort 的 eval 过不了再上 Fable；按 FrontierCode 那组数，Fable High 的成本接近 Opus Max 的一半，值得在你最贵的那类长任务上做一次 effort sweep（从默认 high 开始）对比。
冷水：90% 是厂商自报、没有分母，也不等于人省了 90% 的活——评审和「guidance」的人力没算。基准分大多是各模型最高 effort、开 safeguards，CyScenarioBench 各家题目不同不可直比。Fable 和 Mythos 都要求 30 天数据留存，ZDR 组织默认用不了；开了客户自管密钥的组织连 structured outputs 都没有。

Anthropic 拆解 agent 记忆：告诉模型记忆是干什么用的，别规定它怎么记；再用 dreaming 回放 transcript 纠错

Anthropic2026-11-06 · The components of agent memory

这篇工程博客把「agent 记忆」限定为跨 session、存成可读 context 的经验（不含权重、in-context、compaction），用 CL-Bench、Pokémon、内部文档问答和 Harvey LAB 几组实验拆了三件事：写什么、怎么纠错、怎么组织。

结论一：对强模型，只说「有个 memory 目录可用」效果最好；硬性规则反而伤性能。老模型则相反，需要明确提示「回答前先读记忆、再验证假设」。结论二：在线写下的笔记可能一开始就是错的，「dreaming」——离线拿原始 transcript 校验记忆、改写笔记——能把错误纠回来。结论三：dreaming 可以把记忆整理成互相链接的 wiki，在需要跨文档综合的问题上明显好于纯搜索，但在单文档就能答的任务上没收益，还出现过 wiki 比原文还大、什么都没抽象的情况。并行写同一张共享表会互相覆盖，改成「一个 agent 一份合同、原文逐字引用」后才不丢事实。

  • When we set a rule to “record only failures,” both Opus 5 and Opus 4.7 lost much of the performance boost that memory gave them — CL-Bench 数据库任务，比较的是有无该规则时「记忆带来的增益」。
  • As we scaled dreaming from two sessions to 128, performance on the 25 questions grew from 13% to 48% of graded criteria — 约 35 万文件 / 4.2 亿 token 的 Stainless 内部文档，Opus 5，只用 wiki 作答。
  • Claude had included only 41 of the 57 facts (72%) — 多 agent 写共享表时的结果；改成每份合同单独一页后 57/57。
  • It loads only the first 200 lines or 25 KB of MEMORY.md — Claude Code auto memory 每个 session 预加载的上限。
对你：翻一下你们 CLAUDE.md / 系统 prompt 里关于「记什么」的硬规则，在新模型上 A/B 一次删掉它们。自己的 agent 有记忆目录的，加一个定期的离线任务：拿最近 transcript 对一遍记忆笔记，修正和去重。让多个 subagent 并发写同一份笔记的设计要改成按实体分片、单写者。MEMORY.md 当索引用，控制在 200 行内，细节下沉到子文件。
冷水：多数实验是单次运行、小样本（25 题、24 题），有的是游戏环境；作者也承认 dreaming 要花算力，什么时候跑、校验哪些记忆还是开放问题。
