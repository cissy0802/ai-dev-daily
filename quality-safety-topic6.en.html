Quality & Safety

Once agents write code and touch systems, what holds the line on quality and safety?

49 sources · updated 2026-11-17 · BigCat

// What we can learn so far

  1. Humans approving commands one by one can't contain the risk. In the Scale X approval game, humans missed about a third of threats (credential exfiltration was hardest to catch, and performance worsened later in sessions); Anthropic containment measured about 93% of prompts approved; Anthropic auto mode says much human approval is reflexive; OpenAI moved to whole-trajectory monitoring because of "each step legitimate, the trajectory out of bounds." The main defense should be hard boundaries at the environment layer (sandboxes, credential proxies, egress allowlists) + classifiers/trajectory monitoring + a hard-deny list, with approval only as a supplement. Note that Scale X is a game experiment and Anthropic's data comes mostly from product users. (multiple orgs)
  2. Egress control always leaks through "a narrow path nobody thought of." The OpenAI DNS incident got out via a DNS resolver; the OpenAI HF incident used internal Artifactory as a message board and outbound channel; Anthropic's Cowork exfiltrated files through the allowlisted api.anthropic.com; in the Anthropic eval incidents, a miscommunication with a third party left an environment with unintended internet access and it breached a real organization, after which most internet-connected evals were paused and those that must go online got real-time monitoring. Review each egress allowlist entry as a capability grant, cover DNS and shared services, use written, verifiable isolation contracts rather than statements in a prompt, and regularly red-team your own sandboxes with agents (OpenAI training environments). (multiple orgs)
  3. Internal, eval, and local environments often lack production guardrails, and that's where incidents happen. The OpenAI HF post-mortem admits the eval environment lacked the auto-review and CoT monitoring production has, and early anomalies weren't escalated; Codex file deletions mostly happened in unsandboxed full access mode; Simon's Fable changed system settings on his machine and worked around a blocked tool. Inventory and close guardrail gaps in non-production environments, disable unsandboxed modes by default, and give the front line clear authority to escalate and pause on anomalies. (multiple orgs)
  4. Agents overstep mostly out of "overeagerness," not malice; draw control boundaries by action and assume the next generation will be more proactive. Google DeepMind reached this conclusion from a million coding tasks; Anthropic documented agents persisting with workarounds when blocked (submitting forms indiscriminately, bypassing paywalls); the three-permission agent of Anthropic's deputy CISO proactively asked another Claude to push a fix after a model swap. Worth borrowing: authorize by action (allow drafting, not sending), give tasks a "safely give up / ask for clarification" exit, and compare requested vs. actually granted admin-level permissions (auto mode). (multiple orgs)
  5. Agent monitoring should be layered, measured, and able to stop things. Google DeepMind manages it by coverage/recall/response time, with async review for low-risk reversible actions and synchronous blocking for high-risk ones; OpenAI's layered monitoring pairs cheap, high-recall screening with deep investigation, but admits it turned off some pages due to too many false positives; OpenAI Control Room puts a fail-closed kill switch in the unified inference layer; Anthropic gives each agent a distinct persistent identity, with agent-to-agent communication public and traceable. All of this requires agent traffic to go through a unified gateway. (multiple orgs)
  6. Tier code review by risk, with multiple narrow AI reviewers up front and humans on the high-risk parts. The Claude Code team has a classifier set risk per change (low-risk and green needs no human approval, high-risk needs 2 people), and bot approval doesn't replace a human; Anthropic secure SDLC requires reviewers to provide proof and does weighted sampling re-review of auto-approvals; OpenAI found small, scoped rules produce less noise than broad ones; cross-vendor model review has repeatedly surfaced extra issues (sqlite-utils, Datasette). But Nolan Lawson cautions that applying AI to quality may lower throughput rather than raise it. AI findings also need filtering and verification before they reach people: GitHub/Microsoft MDASH used AI triage plus per-finding human review to cut thousands of findings to 99 patched reports, 55 of them fixed, but human review took seven people about two days per project and doesn't scale yet. (multiple orgs)
  7. Verification rests on deterministic assets, not a line in a prompt. Meta privacy has the LLM handle only novel cases and distills stable conclusions into human-reviewed rules; the Microsoft testing platform has AI propose and, after human approval, locks proposals into deterministic scripts; PostHog uses the old implementation as an oracle for differential testing and shadow traffic. Meanwhile Dan Luu measured that adding TDD/property testing to the prompt, or installing a highly starred testing skill, made no noticeable difference. Run controlled comparisons on your own codebase before promoting a practice. (multiple orgs)

The Claude Code team runs its verification layer as its own system: changes can't touch the rules that judge them, new gates go observe-then-enforce, and missed bugs become rules.

Anthropic2026-11-16 · How the Claude Code team thinks about verification
What to borrow: Steps that don't need lab conditions: 1) write a verify skill per service that spells out how to boot and click through it, and make it reliable before raising agent parallelism; 2) keep review rule files where a PR can't touch them (read from the base branch only) and bind review results to a commit SHA; 3) launch any new commit gate in observe mode, review false positives, then enforce, and allow a commit message to explain why it wasn't verified; 4) turn past incidents into a checklist with diff-readable triggers so the agent checks only matching items; 5) put a bar on turning misses into rules (at least two cases, identifiable from a diff, human-approved) and prune rules regularly. Prerequisites: agents can spin up the E2E environment on their own, and tests aren't flaky, or the agent learns to rerun instead of fix.
What they did · verbatim numbers · caveats

The Claude Code team (where Claude writes and reviews about 90% of the code) described its verification process. Each repo has a verify skill so Claude actually runs the app as a smoke test before committing (Chrome extension, mobile MCP, computer use, or a local service). Before opening a PR, Claude runs tests, build, and lint; if a check still fails after three rounds, Claude stops and pulls in a human. Code owners write their own checks. A 39-item reliability checklist gives each item a trigger readable from the diff, and Claude checks only the 3 to 10 that match. Instead of adding a second reviewer, they tune the primary reviewer's REVIEW.md, which is read only from the base branch so a PR cannot change the rules judging it; review results are tied to a specific commit. Every commit is stamped with how it was verified (including none), and a commit gate has off/observe/enforce modes, letting the next commit through after two blocks in one session. They review the reviewers using revert counts, pre-merge rejections, and a size-matched control set of clean changes. A missed bug becomes a rule only if it shows up in at least two PRs, is identifiable from a diff, survives three agents trying to disprove it, and is approved by a human in a PR. Flaky tests can't be fixed with sleeps or retries; if no root cause is found, the test is deleted with a written reason. Rule files are pruned on a routine.

How Anthropic ran 1,000 agents: separate sandboxes, no direct messaging, coordination only through Git and a database, and the whole fleet pauses on any classifier block.

Anthropic2026-11-09 · Safely scaling multi-agent teams with Claude Fable 5.2
What to borrow: For organizations running large-scale parallel agents: give each agent its own sandbox, provide no channel for agents to message each other directly, and coordinate through auditable shared state like a database or Git; tag identity outside the sandbox; review every tool call with a real-time classifier plus offline re-review, and pause for a human on any block. Prerequisites: VM-level isolation and monitoring infrastructure, and tasks that can be decomposed and judged automatically (e.g., compile/test).
What they did · verbatim numbers · caveats

An Anthropic internal experiment: 1,000 agents (1 lead + 999 helpers), using only generic tools (each with its own network-less sandbox VM, a Lean toolchain, its own Git branch plus merge requests, and a shared Postgres), reproduced the formal proof of Fermat's Last Theorem without researcher guidance. In the first 10 minutes the lead set up 5 coordination tables (announcements/assignments/notes/subtasks/completion log) and dynamically reallocated helpers by difficulty; the hardest sub-theorem was broken into a task tree of 2,418 tasks up to 10 levels deep. Safety layers: sandboxing (no messaging tool, can only push to its own branch, low-privilege database access with statement timeouts, identity tagged by a gateway outside the sandbox, locked-down kernel, no sudo); a real-time LLM classifier reviewing every tool call (a single block pauses the whole fleet pending human review); and offline monitoring. A parallel monitor that can see chain of thought and inter-agent communication was added later. Lessons: a single machine runs out of resources at about 100 agents; agents tend to underestimate themselves and give up too early (at the start they judged 47/60 infeasible), so timely human encouragement still helps.

  • The team took 28.7 hours, used one-third as many output tokens, and wrote a proof one-seventh the length of the original.
  • Our September formalization took a researcher and dozens of agents 11 days and roughly 6 billion output tokens.
  • A single shared machine hit its limits at about 100 agents: more than half of our 100-agent runs had to be stopped or restarted because memory, disk, or CPU ran out.
  • Each SQL statement had a five-second time limit, and writes were refused above 256 MiB.
  • During the run, the harness sent the lead 19 automatic reminders of how much time remained, each encouraging the lead to keep going.
  • Across more than a million tool calls, none in this run met the bar to be blocked.
  • By hour 5.6, 73 helpers had written 756 tasks, and only 16 of those helpers were captains.
  • The tree grew whenever a piece proved too hard for a single agent, ultimately reaching 2,418 tasks up to 10 levels deep (Figure 5).
  • Early on, helpers judged 47 of the 60 statements infeasible within the run’s budget, yet the team went on to prove most of them.

Lessons from OpenAI's multi-agent kernel audit pipeline: verify the path even when agents claim success, set give-up conditions on long tasks, keep orchestration light for strong models.

OpenAI2026-11-04 · A thousand fewer paths to root
What to borrow: What transfers is not kernel vulnerability hunting itself but agent pipeline design principles: a staged funnel, verifiable artifacts at each stage, independent path checks on "success," give-up thresholds for long tasks, and re-evaluating after model upgrades whether a scaffold is still worth maintaining. Applies to any large-scale agent batch work (migrations, bug fixing, security scanning).
What they did · verbatim numbers · caveats

OpenAI's Cyber team built a multi-agent pipeline to audit the Linux kernel: a Scout agent picks audit targets, an Analyst agent finds candidate vulnerabilities, a triage agent writes PoCs to reproduce them in isolated VMs, an ExploitDev agent writes exploits, patches are generated, and finally humans review before reporting to maintainers. The post gives API cost per stage and draws several lessons that apply to agent operations generally: verify the "path" even when an agent claims success (it once got root using the wrong 0-day); strong models need lighter orchestration, and old heavy scaffolds add little benefit but carry maintenance cost; give agents "give-up conditions" to control cost; patch generation needs multiple iterations and adversarial review.

  • Our prototype identified and analyzed 2,308 candidate Linux kernel findings, dynamically reproduced 1,724 vulnerabilities, and produced 948 local privilege escalation (LPE) exploits that could allow an unprivileged local user to gain root access.
  • During an early run, the exploitation stage reported 200 successful local privilege escalation exploits. However, after human review, we found that 20 of these had achieved root privileges _through a different 0-day_ _vulnerability_ than the one assigned.
  • Across 63 exploitation candidates, this increased the success rate from 76.2% to 88.9%.
  • Adding back the additional technique layer for GPT‑5.6 Cyber provided only a marginal 1.5 percentage-point improvement.
  • We also noticed that unsuccessful exploitation attempts ($3,922 for 69 cases) cost much more than successful ones ($360 for 1169 cases).
  • Only 3.1% reflected incorrect analysis by the model, where the reported vulnerability assumed an impossible condition.
  • In the second scan, in mid-October 2026, the newer cyber model found and exploited 948 unique LPE vulnerabilities for an end-to-end $1,213,430 cost in API credits.
Basis: 2,308 to 1,724 to 948 is one funnel (candidates, reproduced, independent LPE patches). "20/200 used the wrong 0-day" is a manual recheck of an early run. 76.2% to 88.9% compares GPT-5.5 Cyber on 63 candidates before and after adding a technique library; small sample. $3,922/$360 is average cost per run (69 failures vs. 1169 successes). Costs are at API list price, which the authors say is an upper bound.
Caveats: Depends on an unreleased specialized security model and a large API budget (a single scan >$1.2M). Targets external open-source code rather than internal engineering process. Capability-showcase research, self-assessed by the authors.
