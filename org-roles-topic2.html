组织与角色

AI-native 之后，岗位、职级、管理方式和团队结构要怎么变？

20 篇来源 · 更新于 2026-11-12 · BigCat

// 目前能学到的

  1. 职级和绩效标准要锚定结果，不要锚定 AI 用量：Amazon 备忘录明说 token 用量、代码变更数一旦变成目标就会导致 tokenmaxxing，只把它们当诊断，并用 P10/P90 找没用好的团队；前 Meta 工程师自述正是反例，「90% AI 代码」成了绩效底线，换来浅测试和脆弱代码。（多个组织）
  2. 管理者要先亲手用：Amazon要求技术和管理 leader 在生产工作中用过、能说清哪里帮不上；Anthropic 工程总监把「经理先当 IC」列为不可协商原则；FurtherAI要求 EM 亲自在 staging 用产品。对带 manager 的人来说，可以从 GitHub 总监的做法起步：用定时自动化接管会前准备、承诺跟踪这类元工作，认可和反馈仍亲自写。（多个组织）
  3. 只推工具只能提高个人速度，团队吞吐要靠改流程：Microsoft Digital称这是「惨痛教训」，原因是每次人与人交接都丢失意图，于是改为团队宪法加 spec 驱动，并由领导把它定为标准；FurtherAI按交付环节逐月改造，并同时度量「代码变更」和「面向客户的变更」，后者增幅更小、来得更晚。（多个组织）
  4. 瓶颈会从写代码转到人的注意力和决策：Anthropic 内部研究发现交互会话约 80% 时间在等人、写 spec 和监控 agent 这类元工作占比翻倍；FurtherAI选择把规划和评审下放给工程师，而不是加管理层；PHP 基金会的严重漏洞卡在共识制决策上，后来改成多数决。组织设计要回答「谁来拍板、多快拍板」。（多个组织）
  5. 角色边界在变模糊，要主动重新划分：PM 用原型代替长文档（微软 Foundry Labs），工程提速后设计成了新瓶颈（Anthropic 设计师），业务一线出现内嵌的工具 PM（Anthropic GTM 架构师），整团队被重新部署去做 prompt 和 eval（Anthropic）。招聘和职级可以参考 FurtherAI「能端到端拥有多大问题」和 OpenAI FDE「学习能力比行业经验重要」。（多个组织）
  6. 把 agent 当队友要有明确规范：Anthropic要求决策写进 agent 看得见的公开渠道、人和 agent 共用一份名册、按任务类型逐步放权；Claude Code 团队的自动评审是按代码区域、花半年以上逐步放开的，核心代码仍由 code owner 审。注意 Anthropic「默认公开」的数据边界比多数大公司宽松，照搬前要先改数据分级政策。（单一组织）
  7. 鼓励个人实验之后，很快需要平台化收口：微软 PM 团队出现多人重复造类似 agent 后转向推广可复用 skill；OpenAI FDE把定制应用收敛为通用 harness 上的 plugin，删掉约 90% 定制代码，用「新团队接入耗时」检验平台化是否成功。（多个组织）

能借鉴的：大公司难以照搬（作者自己说需要允许 agent 打破生产的风险偏好），但可借鉴的局部做法：把历史决策记录成文、做「有先例则自动裁决、无先例才找人」的决策裁判；把不可逆的外部动作放在硬编码闸门后；让 agent 直接消费生产错误与成本异常信号；定期删除为旧模型加的约束。

Anthropic 的 Claude Code 团队用即时规划、按领域专长做人审、经理先当 IC 改写了工程规范

Anthropic2026-06-03 · Running an AI-native engineering org
能借鉴的：对 TLM 很实用的清单：用即时规划替代长路线图、把「问作者」改为「先问 agent 再问能否自动化」、按领域专长而非全量做人审、经理先做 IC、给团队「砍流程」的明确授权、用入职爬坡时间/PR 周期/AI 辅助提交占比作为采纳度指标（同时警惕只看吞吐）。前提是有足够的 CI 容量与内部用户群可快速反馈。
做了什么 · 原句数字 · 冷水

Claude Code/Cowork 工程总监（Code w/ Claude SF 2026 演讲整理）介绍团队在 agent 编码成为默认后改写的规范：规划从 6 个月路线图改为「即时规划」（PR/原型中讨论、先给内部用户用再迭代，少做产品评审）；找上下文先问 Claude 而不是找作者，并追问「这件事能否自动化」；代码评审由 Claude 处理风格/lint/bug/补测试，人只在需要领域专长处介入（法务风险、信任边界与安全代码、PM/设计的产品品味）；角色模糊化——PM 大量写代码、工程师承担内容和设计，招聘偏重「有产品感的创造型 builder」和「深系统专长」两类，不看重原始产出量。推行方式：少数不可协商的团队原则（全员 dogfood、团队尽量扁平且经理先当 IC、明确授权砍掉过时流程），其余由各 pod 自主。建议追踪三个指标：入职爬坡时间、PR 周期时间、Claude 辅助提交占比，但提醒吞吐不等于成功。

  • When I first joined the Claude Code team, we wrote a pretty good six month roadmap, and then because of Claude Code, so many things changed that it was out of date by month three.
  • For us, by default, every commit is Claude-assisted. I don't think I've seen a non-Claude-assisted commit in the last four months.
口径：无系统性数据；「每个 commit 都由 Claude 辅助」是总监个人观察，未定义「辅助」。入职爬坡、PR 周期只给了「比一年前快很多」「第一周就能交付真实代码」的定性描述。
冷水：产品团队负责人演讲，带产品推广；Claude Code 团队做的就是 agent 工具本身，dogfood 条件与一般业务团队不同；无量化验证。
