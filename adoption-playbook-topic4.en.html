AI-NATIVE · ADOPTION-PLAYBOOK

Adoption Playbook

In a large non-lab organization, how do you stage an AI-native transformation, measure it, and control cost and risk?

13 sources · updated 2026-11-13 · BigCat

// What we can learn so far

  1. Use input metrics for diagnosis, never as targets: once token usage, adoption rate, or PR counts become targets, they breed tokenmaxxing and line-count inflation. A better view looks at both tails: P10 to find teams that aren't using AI well, P90 to check whether heavy users actually deliver more (Amazon). Write down expected value and baseline before launch, review monthly, and track where saved time is reinvested (Microsoft measurement framework). The counterexample is the Microsoft Cowork rollout: with no telemetry or campaign tags in place before launch, it couldn't tell afterward which promotion drove usage. When computing AI value, include review and rework costs (OpenAI finance). (multiple orgs)
  2. Transform one delivery stage at a time rather than rolling out everything at once. FurtherAI advanced month by month: agents write code → write tests → AI pre-review → parallelized CI → automatic bug intake → verbal rules turned into checks → auto-merge for low-risk changes. It tracked both "merged changes per person per day" (about 5x) and "customer-facing changes"; the latter grew less and lagged, and was flat during the summer tooling investment. Accept an investment dip during the transition up front, and note that this is a small AI-native startup with far less process overhead than a large company. (single org)
  3. Approaches to governing AI coding costs diverge. Databricks uses internal evals to shift usage to cheaper models, adds gateway routing, then applies progressive friction (dashboards → self-clearable gates → downgrades → pausing only as a last resort) to avoid hurting high-output users. Uber, after spending its full-year budget in four months, set a hard cap of $1,500 per person per tool per month. The OpenAI CFO argues for managing AI spend like a variable expense, with budgets, routing, and approval thresholds. All of this requires agent traffic to go through a unified, meterable gateway. Also note that Databricks' 30%/50% savings are its own internal results, and it sells gateway products. (multiple orgs)
  4. Pilots should be small, with a team committed to giving feedback, and feedback turned into rules immediately. The Anthropic marketing team first gave the tool to a 10-person sales group and wrote every piece of feedback as an explicit rule (e.g. "never fabricate URLs"), accumulating 9 in the first week; expanding to BDRs later took only two days. The security equivalent is "admin-paced" rollout: a small group first, watch telemetry, then expand (Anthropic CISO). Use hackathons to give the front line time to rework their processes, with technical staff pairing alongside (OpenAI finance). After a company-wide rollout, launch day is only the start: Microsoft Cowork drove usage by collecting colleagues' real prompts and outputs, sending reminders for months, and adding plugins that connect to everyday systems (adoption data only, no outcome data). (multiple orgs)
  5. Leaders and employees alike need hands-on experience, and need to acknowledge the limits. Amazon requires technical and management leaders to have used the tools in production work and to be able to say which tasks they helped with and which they didn't; "AI didn't help" counts as a finding, not a failure. Leveling criteria are anchored on outcomes and don't name specific tools. Anthropic puts mindset principles such as "scale verification effort to risk" into company-wide onboarding, in place of prompting tips that quickly go stale. When non-engineering roles pick their first tasks, the Cowork five-point checklist helps judge whether a task suits an agent. (multiple orgs)
  6. Every agent use case can first go through a four-question security review: what untrusted content it ingests, what actions it can take and as whom, how big the blast radius is if it goes wrong, and what observability exists. Trim authorization at the action level (e.g. allow drafting, not sending), keep credentials worth stealing out of the agent's environment, and have an org-wide one-click kill switch. Let non-engineering teams build agents on a managed platform to reduce shadow AI (Anthropic CISO). In the case cited, upgrading only the model was enough for an agent to proactively ask another Claude to open a fix PR, which shows boundaries must be drawn by permissions, not by assumptions about model capability. (single org)
  7. Shared skills and plugins are how "individual usage" becomes "organizational workflow." Skill governance can be decentralized: start in a sandbox, move into the marketplace once there's traction, track usage with hooks, and put effort into verification skills first (Anthropic skills). OpenAI uses "95% of employees use Plugins weekly" as a reference point for deep adoption (OpenAI Enterprise Signals), but its denominator is inconsistent (employees vs. active users), and neither post has outcome data. (vendor self-reported)

Microsoft's internal agent rollout review: provisioning isn't adoption; peers' real prompts and months of nudges drove use, but with no pre-launch baseline, impact can't be attributed.

Microsoft2026-11-12 · Making AI adoption stick: What we learned after launching Copilot Cowork at Microsoft
What to borrow: When rolling out agent tools, treat the 2-3 months after launch as the main effort. Build peer story collection (real prompts + real outputs) into the launch plan from the start; it does more than a feature list to help people imagine "what I could hand off to it." And instrument usage telemetry and campaign markers before launch so you can line up campaign timing with the adoption curve. Prerequisite: a small team that can keep an internal community running and route feedback back to the product owner. One more borrowable idea: write documentation so "both people and AI can find it," and measure "finding the right answer," not just clicks.
What they did · verbatim numbers · caveats

After Microsoft Digital (the company's IT organization) launched Copilot Cowork (an agent that runs multi-step tasks across M365 and the web) at an all-hands in April, it did not treat launch as the finish line. It formed a virtual team across IT, product, and marketing, splitting ownership of promotion, user feedback, and routing product requirements back. In June it started #HowICowork, asking employees to post their real prompts and outputs, alongside editable sample prompts, and built plugins such as Azure DevOps and Chart to connect the agent to more everyday systems. These employee stories were later packaged into customer-facing sales material. In the review they admit there was no clean pre-launch baseline, so they cannot show which push drove growth.

  • The campaign reached about 58% of our employees, and 45 people shared their own Copilot Cowork prompts and stories.
  • Over the same period, weekly active Cowork users grew 27%, from about 35,000 to nearly 45,000 employees.
  • Between mid-August and early October, monthly active users grew from about 60,000 to 70,900.
  • By early October, Cowork also had 52,400 weekly active users and 27,800 daily active users.
  • A quick reality check: This data doesn’t prove that any one email or post caused a bump, and we didn’t have a clean baseline from before launch to compare against.
Basis: 58% is campaign reach, not usage rate; only 45 people shared stories. WAU going from 35,000 to 45,000 was "concurrent" with the campaign, and the authors themselves say there is no pre-launch baseline and it cannot be attributed. MAU/WAU/DAU are activity counts with no definition of "active," and there are no output or quality metrics; total headcount is not given, so penetration cannot be calculated.
Caveats: Microsoft is the vendor of Cowork, and Inside Track doubles as external marketing (it ends with a sales funnel). Only adoption data, no impact data. Growth can't be separated from organic spread and product improvements, as the authors acknowledge.

FurtherAI rebuilt its delivery pipeline one stage per month while tracking two throughputs: code changes and customer-facing changes.

FurtherAI2026-10-29 · Building an AI-native engineering org
What to borrow: The closest thing to a roadmap a non-lab company could copy: rebuild delivery stage by stage, month by month (code, tests, review, CI, bug intake, rules as checks, low-risk auto-merge, Slack code channel), measure both "code changes" and "customer-facing changes" throughput, and accept the investment dip during the transition. Turning reviewers' unwritten rules into CI checks that print the fix is the prerequisite for agents to self-correct and for opening up low-risk auto-merge.
What they did · verbatim numbers · caveats

FurtherAI's CTO reviews nine months of AI-native transformation, rebuilding the delivery pipeline one stage per month: March, agents write code; April, agents write tests; May, AI pre-reviews nearly every change; June, parallelized CI that runs only affected tests; July, Claude Tag automatically picks up bugs from Slack, dedupes, and assigns them; August, "rules only engineers know" became Python checks that run on every commit, and low-risk changes auto-merge; September, a "code channel" lets anyone ask an agent in Slack to open a PR. They built Poirot/Sherlock troubleshooting agents (read-only DB). Organizationally, the bottleneck moved to "deciding what to build" and review; they chose to push planning/execution/review down to engineers rather than add management layers, redefined levels by "how big a problem you can own end to end," and require EMs to use the product themselves in staging and understand it better.

  • Since January, the number of code changes each engineer merges a day has grown about 5x, while our revert rate has stayed under half a percent.
  • Tests (April) – Agents write tests alongside code. 91% of changes now include tests, up from 15%.
  • Review (May) – AI reviews 99% of changes before a person does, up from 60%.
  • CI now runs 20× the tests in the same 17 minutes.
  • It now files 60% of bug tickets.
  • We went from zero to 21 rules.
  • Up to a third of our changes now merge without a person involved.
  • Our designer has merged about 50 changes since August, including the ones that built our design system.
  • Through the summer, much of our engineering effort went into tests and tooling, and customer-facing changes per engineer stayed between 17 and 30 a month.
  • In September, that jumped to 45. October is on pace for 48.
  • Planning and review now account for 70% of the time, up from 40%.
Basis: "5x merged changes per engineer per day" and "customer-facing changes per person per month" are different measures; the latter grew less and lagged (flat during the summer tooling investment period). 70% vs. 40% is the author's simplified illustrative calculation, not a measurement. Team size not disclosed.
Caveats: Startup CTO self-report ending with a hiring pitch; small team, AI-native business, with far less scale and process overhead than a large company; numbers not independently verified.

Amazon's level guidelines name no AI tools and anchor on outcomes; input metrics like tokens are for diagnosis only.

Amazon2026-10-27 · An update from Amazon engineering leadership on the role of the developer in the age of AI
What to borrow: The most direct template for large non-lab companies: anchor level/performance criteria on outcomes, not AI usage; use input metrics for diagnosis, not as targets; use P10/P90 percentiles rather than averages to find problem teams; require leaders to have hands-on experience and be able to articulate the limits; allow and encourage engineers to document and share cases where "AI doesn't apply."
What they did · verbatim numbers · caveats

Amazon's senior principal/distinguished engineer community revised the SDE role guidelines and sent an all-hands memo. They deliberately kept specific AI tools and practices out of level criteria (so they won't be stale in a year) and anchored instead on "outcomes for customers, the business, and the team." They acknowledge using input/throughput metrics such as token usage, AI tool adoption, and code change and review counts, and state plainly that treating these as targets leads to tokenmaxxing and LOC bloat. They recommend focusing on P10 of AI adoption (find teams not using it well and understand why) and P90 (whether heavy users show a matching delivery gain). Technical and management leaders must have used these tools hands-on in production work and be able to name the tasks where they helped and where they didn't. "AI can't help with your work" is defined as a finding, not a failure.

Caveats: An internal memo published externally, with employer-branding and AWS marketing elements; no data backs its claim that "input metrics correlate with output."

An Anthropic marketer piloted with a 10-person group, turned every piece of feedback into an explicit rule, then rolled out to the entire sales org.

Anthropic2026-08-24 · How an Anthropic field marketer uses Claude Code to send weekly personalized updates to every sales rep
What to borrow: A rollout method you can borrow directly: use internal hackathons to carve out time for non-engineering teams to rebuild workflows; run small, committed pilots; turn every piece of user feedback into an explicit rule (especially hard constraints against fabrication); version the prompt and move it into Git once several people maintain it. Note that the author later dropped pre-send approval; non-lab organizations should first weigh the cost of erroneous messages going out.
What they did · verbatim numbers · caveats

During an internal "marketing hackathon," Anthropic's marketing team used Claude Code plus a BigQuery MCP to replace the Monday sales standup deck with a Slack weekly digest tailored to each AE (matching events, content, and registered contacts to their CRM territory). They piloted with a 10-person sales group and wrote every piece of feedback into the prompt as an explicit rule (e.g., Claude once invented URLs for events missing links, so a hard rule now says "never invent URLs" and links must come verbatim from the source table); by the end of week one there were 9 rules. Each run first reads the table headers to validate column mappings, guarding against source schema changes. It then rolled out to all of sales, BDRs (live in two days), customer success, and alliances; the prompt was versioned and moved to GitHub.

  • Sending to a group of 10 people felt less daunting in case errors came up, and the group was committed to providing feedback.
  • By the end of the first week, the prompt held nine content rules, each traced to a piece of feedback from a seller or a manager.
  • The field events sheet, for example, has had its columns rearranged three times in six weeks.
  • The digest is working; we recently doubled registrations for an executive dinner in a week, purely because the right reps had the right event in front of them on Monday morning.
  • The prompt structure and content rules carried over unchanged, and the BDRs were live within two days.
Basis: "Dinner registrations doubled" is a before/after comparison for a single event with no control, and the attribution is the author's inference; other figures are process counts.
Caveats: Employee account plus product promotion; screenshots use synthetic data; the results metric is a single anecdote.

Databricks manages AI coding costs with internal evals, model routing, and graduated spend gates rather than blunt hard budgets.

Databricks2026-08-07 · Managing AI Coding Costs at Scale
What to borrow: The most directly copyable piece for non-lab enterprises: build your own internal coding evals to decide which models to enable; meter everything through a gateway; replace hard budgets with graduated friction (dashboard → self-clearable gate → approval → downgrade → pause) so you don't hurt your most productive users. Prerequisite: all agent traffic goes through one gateway.
What they did · verbatim numbers · caveats

Databricks summarizes AI coding cost governance at itself and at Stripe, Coinbase, Uber, and Ramp. The biggest lever is using internal evals to keep moving usage to cheaper models on the "efficiency frontier" (Databricks pushed GLM based on its internal benchmark; Stripe did not enable Opus 4.7 because it showed no quality gain). Request- and task-level routing goes through a meta-harness and an AI gateway. Instead of blunt hard budgets: real-time usage dashboards, self-clearable spend gates, and downgrading to cheaper models on overage, with pausing only as a last resort. Tuning harness and cache settings trims token spend.

  • Internal results at Databricks suggest that our AI Gateway Smart Router is able to consistently reduce average task cost by more than 30%, while roughly matching the quality of the most expensive model in the working set.
  • At Databricks, relatively simple tuning of our harness and caching settings led to an almost 50% reduction in the number of generated tokens and associated costs, with no observed quality degradation for developers.
Basis: The post itself calls the savings percentages in its summary table "directional, based on an informal survey of development teams"; 30%/50% are Databricks internal results, with no detail on how quality was judged.
Caveats: Databricks is selling its own Unity Gateway/Omnigent; other companies' practices are relayed from interviews, not first-hand data; the "velocity metric improvement" has no number.

Anthropic's deputy CISO vets agent use cases with four questions, draws boundaries by access and action, and assumes the next model will be more proactive.

Anthropic2026-07-17 · Zero risk isn't the job: a CISO's guide to agentic AI
What to borrow: Usable directly as a security review template: four-question assessment + least-privilege agent permissions + small-scope first. Govern agents as insider risk (identity, least privilege, monitoring, minute-level response). Let non-engineering teams build agents on a managed platform to reduce shadow AI. Trim connector capabilities at the action level. Design controls assuming the next model will be more proactive. Requires foundational security infrastructure such as IdP/SCIM, SIEM, and an egress proxy.
What they did · verbatim numbers · caveats

Anthropic's deputy CISO describes the four questions used internally to approve agent use cases (what untrusted content it ingests, what actions it can take and as whom, the blast radius if it goes wrong, what observability exists), with an "admin-paced rollout" as the default (a small group first, watch telemetry, then expand). Case: a security incident response agent launched over a year ago has just three permissions (read-only, PII-free production logs; opening Slack channels; drafting postmortem docs), and every action goes to the SIEM. In November 2025, after only the model was upgraded and nothing else changed, it for the first time proactively asked another internal Claude instance that can write code, via Slack, to open a fix PR while no human was present; a human reviewed it before it shipped. The lesson: draw boundaries by access and action, not by assumptions about model capability. Agent-to-agent Slack communication with human oversight is now routine. Internal principles: the environment where the agent loop runs holds no credentials worth stealing (a reverse proxy injects credentials); mandatory egress proxy and allowlist; authorize by action, not just by connector (allow drafting, not sending); telemetry goes via OTel into the SIEM; an org-wide one-click kill switch. Non-engineers on the GRC team build their own agents with Claude Code on an internal hosting platform for business apps (security questionnaires, vendor and subprocessor change review), which is treated as visible, "non-shadow" adoption.

  • As of July 2026, more than 50% of all code submitted for pull requests at Anthropic is authored by our internal version of a Claude Tag-like system.
Basis: The denominator for "over 50%" is "all code submitted to PRs," with no stated unit (lines/PRs). It is a different metric from the same author's other claim that "more than half of code is merged by internal Claude Tag" and from "80% of code written by Claude" (who submits/merges vs. who writes).
Caveats: The deputy CISO's own account, heavily promoting Cowork/Enterprise admin controls; the incident response agent's "unexpected behavior" case may have been selected; no counts of blocks or incidents.
