销售、财务、法务、市场、数据等非工程团队，怎么把 agent 用到实处？

// 目前能学到的

  1. 准确率主要是上下文和验证的工程问题，换更强的模型解决不了：Anthropic 数据团队没有 skill 时 eval 准确率不超过 21%，加上 skill 后超过 95%，但一个月不维护就漂移到约 65%，于是把 skill 和数据模型放进同一个 PR；GitHub Qubot让各数据 owner 贡献上下文，每次变更都过 eval；微软 PM 团队遇到报告不准时先修源数据。（多个组织）
  2. 对外发送和对系统记录的修改，保留人工批准：Anthropic BDR的 CRM 更新走「提议+证据+人工批准」并记录驳回原因；Anthropic 财务和 OpenAI CFO都是 AI 出初稿、人签字；Anthropic 法务用 AI 初审、律师复核标记项的双层流程。Anthropic 市场后来取消了发送前审批，非实验室组织要先评估错误外发的代价。（多个组织）
  3. 把每次人工纠正固化下来，让它长期生效：Anthropic 市场第一周就把反馈写成 9 条显式规则（包括「绝不编造 URL」）；Anthropic 法务每周让 Claude 根据律师反馈提议更新指令，批准后才生效；Meta把专家修正走 eval、回归测试、PR 审核后再并入知识文件。（多个组织）
  4. 从窄而重复的任务起步：Anthropic 增长营销的「五要素」（多个输入、产出一个文件、会重复做、知道好结果什么样、中间是枯燥的汇编对账）可以直接用来挑首批任务；GitHub 法务从一类通知的分诊起步，把方法论写成仓库里的纯文本指令；OpenAI 财务用黑客松让一线带问题来、技术人员陪跑。（多个组织）
  5. 个人工具要经过验证再进团队共享库，并配人负责：Anthropic BDR的 skill 先个人验证再升进团队 plugin；Anthropic 销售的工具打包成 plugin、作为新人入职默认配置，做工具的人转成了专职 GTM 架构师（「约 80% 销售在用」没有定义使用口径）；微软 PM出现重复造 agent 后改推可复用 skill。（多个组织）
  6. 运维护栏要按生产系统的标准来做：Anthropic 日本 BDR凭证集中托管、按 agent 最小授权、指令改动有版本；Anthropic 数据 agent只读治理层、PII 列级屏蔽、每条查询打请求人标签；Meta 隐私分类先用确定性规则处理约 85% 请求，LLM 只兜底；GitHub 市场的定时任务因为没有失败告警，静默失败了五天。微软业务运营的数字员工有独立身份、按职能授权（能建单不能删单），而且在规模化之前就要定好开通、成本分摊和退役机制。（多个组织）
  7. 这一类的效果数字几乎都是单人自估，而且来自厂商的推广系列：比如 Anthropic 市场运营「两天缩到两小时」、日本 BDR「省约 60 小时」；Anthropic 购买 agent「转化 2 倍」的对照组是客户自选的。微软 BPO「人工接触减少 75%」也没说怎么计数。可以借鉴做法，效果要用自己的基线重新测。（厂商自报）

Microsoft2026-11-17 · When digital workers need a computer: How we’re using Windows 365 for Agents at Microsoft
能借鉴的：给非工程运营团队上 agent 时可以照抄的顺序：1）先挑重复量大、摩擦高的流程，把步骤、数据和策略理顺，坏流程不要直接自动化；2）执行方式从简到繁：有 API 或确定性自动化就用它，只有必须操作 UI 的步骤才给 agent 一台受管电脑；3）从第一天起给 agent 独立身份和按职能的最小权限模板（能创建不能删除），不要复制员工账号；4）规模化前把 owner、开通、监控、成本分摊、退役写成运营模型，并让 FinOps 参与；5）例外交给人时附上 agent 已做了什么、卡在哪、之后会发生什么。前提：IT 能为 agent 发身份和设备，有可观测的审计记录。
做了什么 · 原句数字 · 冷水

微软业务运营（报价到回款、合规、合作伙伴流程）和内部 IT（Microsoft Digital）一起，在一个运营单元试点「数字员工」：用内部的 BPO AI Toolkit 把操作知识转成流程指令、策略和可复用 agent 能力，编排 agent 按需调用 skill；遇到没有可靠 API、校验藏在 UI 里的老系统，就借一台托管 Cloud PC 像人一样操作。他们的做法是先用持续改进（他们叫「CI + AI」）简化流程和数据，再上 agent；agent 用专门的身份认证，按功能授权（能建订单不能取消或删除），网络只放行所需端点，而不是复制员工权限；执行中留证据，遇到例外带上下文升级给人。落地时最难的是给 agent 开通 Cloud PC、分配身份和许可证、计费，这些原本要租户管理员手动操作，于是和 FinOps 一起做用量上限和成本分摊，并要求提前定好 owner、监控和退役机制。

  • The BPO AI Toolkit has reduced human touch by 75% and cut cycle time from 25 to 10.3 hours, while completing thousands of orders with no rework.
  • With Windows 365 for Agents, the team has a path to further reduce human touch by up to 95% and processing time to four hours.
口径：「人工接触减少 75%」没有说怎么数接触（步骤、工时还是人次），也没说是哪个流程、多长时间、多少订单的基线；「25 小时降到 10.3 小时」的周期时间同样没有样本和时间段。「几千单零返工」没有给总单量和以前的返工率。「最多 95%、4 小时」是未来目标，不是结果。数字是 BPO Toolkit 的，Windows 365 for Agents 本身对这些数字的贡献没有单独给出。
冷水：厂商自报的 Customer Zero 帖：微软在推 Windows 365 for Agents 和 Marketplace 上的工作台，文中多处是产品经理的引语；只有一个运营单元的试点，仍在分阶段推广；效果数字口径不清，而且混了未来目标。

能借鉴的：非常可迁移：先做少量 canonical 数据集 + 几十条离线 eval + 一个薄的路由 skill；skill/文档与数据模型同仓同 PR，CI/评审 hook 强制同步；eval 结果按版本入仓当遥测；按域设准确率门槛再开放；用户纠正自动转 PR 和 eval；回答附溯源脚注。前提是已有数据治理基础（语义层、元数据、owner），人工维护定义而非让 LLM 自动生成指标定义（文中说那样在 eval 上是净负）。
做了什么 · 原句数字 · 冷水

Anthropic 数据科学/数据工程团队把业务分析查询大部分交给 Claude，并把准确率当作「上下文与验证」问题而非写 SQL 问题：收敛为少量强治理的 canonical 数据集并用工具/CI/行政要求强制使用；skill 强制先走语义层，再走按域整理的参考文档；skill 文档与数据模型同仓，评审 hook 拦截未同步 skill 的报表模型改动。验证体系：离线 eval（看板问题自动生成+人工确认、长尾问题、用户纠正自动收集为候选 eval），结果按 skill 版本/git SHA/模型 ID 入仓当遥测；按业务域设上线门槛（初始约 90%）；每次 skill 改动做单变量消融；线上用对抗式复核 sub-agent、溯源脚注（来源层级/新鲜度/owner）、定时 agent 扫描频道中的纠正语言并自动开 PR 给域 owner；面向管理层的结论必须人工签字。

  • At Anthropic, 95% of business analytics queries are automated via Claude, with ~95% accuracy in aggregate.
  • Without skills, Claude’s ability to answer analytics questions accurately didn’t exceed 21% on our evals.
  • Adding skills gets these numbers consistently above 95% in aggregate and regularly around 99% in certain domains.
  • We watched our offline accuracy drift from ~95% at launch to ~65% over a month before we treated this as an engineering problem.
  • Roughly 90% of our data-model PRs now include a skill change in the same diff.
  • Gate launches per domain: A domain owner can't announce the agent to their stakeholders until their slice of the eval set clears some threshold (we initially used ~90%).
  • Accuracy moved by less than a point in either direction.
  • About 80% of the time, yes.
  • Adversarial review: we’ve found that employing a Claude skill to aggressively challenge all underlying assumptions on a potential final answer increased accuracy by 6% within our eval set, but at the cost of 32% more tokens and 72% higher latency.
口径：「95% 查询自动化」的分母是业务分析查询（未定义统计口径与时间窗）；「~95% 准确率」是离线 eval 的汇总准确率，作者自己强调离线 eval 不代表线上表现、且静默错误仍无可靠解法。21%→95% 是有无 skill 在同一 eval 集上的对比。95%→65% 是上线后一个月未维护文档时的离线漂移。90% 是数据模型 PR 中同时改 skill 的比例。6%/32%/72% 是对抗复核的准确率/token/延迟增量。
冷水：自述的准确率基于自建 eval，覆盖度未知；Anthropic 内部数据规模与业务复杂度和一般企业不同；文章同时推广 Claude Code/skills。
