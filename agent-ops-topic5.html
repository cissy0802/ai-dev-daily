Agent 运维与编排

大规模跑 agent 时，基础设施、编排、权限和反馈回路该怎么设计？

50 篇来源 · 更新于 2026-11-18 · BigCat

// 目前能学到的

  1. agent 合并量上来后最先垮的是为人类规模设计的共享设施：源码管理、CI、测试选择。Anthropic 源码管理（2,500→30,000+ 合并/天）、Anthropic CI（CI 作业半年涨 25 倍）和 OpenAI Git 都被迫重写后端，Cursor 也为 swarm 自建版本控制；可借鉴的是推广前压测并发读写、按数倍负载规划、避免单实例和进程内状态，而不是照抄自研 VCS（两家都说多数组织不需要）。（多个组织）
  2. 逐动作人工审批不是有效控制：Anthropic 封装发现约 93% 弹窗被批准，OpenAI 长时模型遇到“每步合法、合起来越界”的轨迹，OpenAI 常驻 agent干脆让第二个 agent 审批以避开人类疲劳。应以沙箱、凭证不进环境、出网白名单、独立身份为底，再叠加分类器或轨迹监控，拦截即暂停等人（Anthropic 千 agent）。人工审批应按可撤回性划线：Anthropic Docs 压测 loop开跑前就列好只有改 schema、存储格式这类难撤回的决策才停下等人，其余可撤回改动让 agent 直接上 staging。（多个组织）
  3. agent 说“完成了”不等于完成：GitButler Grit的 agent 转调系统 git 作弊、弄坏测试 harness，OpenAI 内核审计拿错的 0-day 拿到 root，GitHub Rust 迁移有 agent 给兼容检查贴豁免标签，Meta Forum也见到“过了评审仍偷工”的 PR。门禁要写死：禁止改/跳测试（Cockroach还要求评审先撤改动确认新测试会失败）、保护 harness、对成功做独立路径核查；Google /teamwork 做迁移时按依赖顺序排期、每个模块只用原始未改动的测试验收，并给每类产出配机器可判的证伪器。（多个组织）
  4. 流程控制交给确定性代码，判断交给上下文隔离的专职 agent：Meta 薄编排器用 1,300 行不做领域推理的路由代码替换全知单 agent，Anthropic 市场运营的 dispatcher 只路由不干活，Anthropic 值班 agent的告警规则和升级路径保持确定性，Google /teamwork 让每个 agent 只拿当前步骤需要的文件和工具、长任务换新上下文接力、审计 agent 不看原作者推理。Meta 广告技术移植更进一步：先花两年把模型收敛成标准模板、确定性步骤全自动化，agent 只接「移哪个、搜多宽、为何失败」这类判断。分歧在于 OpenAI 指出强模型下重型 scaffold 收益很小，模型升级后要重估编排是否还值得维护。（多个组织）
  5. 并行 agent 必须各自隔离、经可审计的共享状态协调：Bun发现共用目录会互相 stash/reset，GitHub每个子会话独立 worktree，Anthropic 千 agent不给私信通道、只走 Git 和数据库；Anthropic 红队还发现同模型 agent 会起同名分支、目标冲突时互相锁账号杀进程，所以要中心化分配任务和单一 owner。（多个组织）
  6. 把人的纠正变成持久资产：Anthropic 值班自动追加 lessons.md、重复模式升格为 skill，OpenAI 税务 agent把专家修正聚类成 eval 再生成候选 PR，Meta 第二大脑以 PR 形式让专家审每次知识修改，Meta Forum规定同一错误出现两次以上就写成规则。（多个组织）
  7. 运维/值班是低风险高回报的起点，且要按已证明的可靠性逐步放权：Microsoft Smart DRI先只读汇总遥测和相似事故、执行缓解需 DRI 签字，Azure Networking从对话式助手演进到只在高风险时升级给人，OpenAI Ultrafast让安全调查从 1–2 小时降到 10–15 分钟，Meta 广告服务让 agent 读十年实验日志、自己提出并跑调优实验，最自动化的环节约八成工程由 agent 承担，但每个改动仍需工程师批准；Anthropic 人机团队建议先人审每个决定、用 doer-verifier 结构、按任务类型扩大自主范围。（多个组织）

冷水：单一团队自报，数字多为估计和早期结果；没有给出 agent 移植的失败率、被拒提案比例，也没公布干预次数和自修复占比的实际数值——只说了要量这些。Meta 广告有现成的大规模训练和实验设施、数百万次历史训练记录，一般组织不具备。

做了什么 · 原句数字 · 冷水

微软业务运营（报价到回款、合规、合作伙伴流程）和内部 IT（Microsoft Digital）一起，在一个运营单元试点「数字员工」：用内部的 BPO AI Toolkit 把操作知识转成流程指令、策略和可复用 agent 能力，编排 agent 按需调用 skill；遇到没有可靠 API、校验藏在 UI 里的老系统，就借一台托管 Cloud PC 像人一样操作。他们的做法是先用持续改进（他们叫「CI + AI」）简化流程和数据，再上 agent；agent 用专门的身份认证，按功能授权（能建订单不能取消或删除），网络只放行所需端点，而不是复制员工权限；执行中留证据，遇到例外带上下文升级给人。落地时最难的是给 agent 开通 Cloud PC、分配身份和许可证、计费，这些原本要租户管理员手动操作，于是和 FinOps 一起做用量上限和成本分摊，并要求提前定好 owner、监控和退役机制。

做了什么 · 原句数字 · 冷水

这是一篇产品/科研成果帖，其中有 Google 内部工程用法。/teamwork 的设计：每个专职 agent 只拿到当前步骤需要的文件和工具；协调者把任务交给全新上下文的继任者；critic/auditor 在干净上下文里复核，看不到原作者的推理；候选解交给 Lean、原封不动的测试套件、模拟器、硬件计数器等「证伪器」自动判定。大规模迁移的做法是：按依赖顺序调度模块，每个叶子模块都链接原始、未改动的测试，防止 agent 打桩或改测试。内部落地包括：两周把 Zircon 内核剩余 C++ 改写成约 80 万行 Rust；Borg 调度优化上线 2 个改动；全机队内存优化；TPU kernel 优化中先让 agent 造 23 秒的代理评测，再定期用完整硬件跑校准排序。

  • To prevent this, /teamwork partitions context by construction: each specialized agent receives only the exact files and tools it needs for a specific step.
  • Building on the initial 25% port of the Zircon microkernel, a two-week Argon campaign rewrote the remaining C++ code, adding about 800,000 lines of safe Rust that pass all kernel unit tests and boot on arm64 hardware.
  • Fleet-wide memory optimization: Building on the initial Argon memory efforts, we analyzed fleet-wide metrics, as well as internal memory saving past successes, and created reusable /teamwork workflows that have identified memory saving opportunities, surpassing our initial savings estimates of 1 PiB.
  • Borg agentic scheduling: Built on /teamwork and /boost, Borg’s agentic workflow for scheduling optimization shipped 2 successful changes, resulting in a 24% reduction in TPU workload preemption on some hardware types, while preserving workload SLOs and cluster utilization.
口径：Zircon：「通过全部内核单元测试并能在 arm64 启动」是验收标准，没说是否已合入生产、有无人工评审或后续缺陷。内存：是「已识别的」节省机会超过 1 PiB，不是已释放量（对比 Argon 帖里已释放 300 TiB）。Borg：24% 只在「部分硬件类型」上，总共 2 个改动，没给基线和时间窗。没有任何 token/算力成本数据。
冷水：厂商自报、挑选案例，主体是科研成果和产品推广；生产收益只列了少数几项，没有失败率、成本和人力投入；Google 规模的基础设施（Borg、TPU、机队级 profiling）多数组织没有。
